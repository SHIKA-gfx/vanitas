# 005. 픽업 플래너 설계 (v0.2)

> 작성: 2026-10-24 · 상태: 설계 확정, 데이터 초안 검토 중
> 관련: 기획서 3-4, `docs/004`(경쟁 서비스·데이터 출처 정책), 개발 결정 문서 1장 "천장 규칙은 날짜의 함수"·"스택 방식 계산"

## 1. 무엇을 답하는가

> **고른 학생들을 지금 재화와 앞으로의 수급으로, 우선순위대로 몇 명까지 확정으로 데려올 수 있고,
> 그러려면 픽업마다 얼마를 쓰고 얼마를 남겨야 하나.**

답은 세 겹이다.

- **판정**: 목표마다 확보 가능 / N개 부족 / 불가(이유)
- **행동**: 픽업 기간마다 몇 연 / 넘기기, 그 시점 잔고
- **대안**: 무엇을 포기하면 무엇이 되나 (최대 2개)

하지 않는 것

- 학생 성능 평가·추천 — 주관이 크고 커뮤니티 평가글의 영역
- 일정 안내 자체 — 일정은 고르기 위한 재료
- 과금 권유 — 부족분은 청휘석 개수로만 말한다

## 2. 범위 (v0.2)

- **모집 스택 방식만 다룬다.** 플래너는 2026-11-10 전환 뒤에 공개되므로 계획 대상 픽업은 모두 스택 시대다. 포인트 방식·전환일을 가로지르는 계산은 없다
- **목표는 "확정(천장까지)" 하나뿐** (2026-10-24 결정). "반천장까지만"은 v0.2 다음으로 미룬다 —
  그 학생에게는 못 얻는 경우가 최악이지만 뒤의 목표에게는 얻는 경우(스택 초기화)가 최악이라, 안전 계획 하나로 묶을 수 없다
- 학생 한 명당 1장. 중복 획득(신비 해방 등)은 다루지 않는다

## 3. 판정 기준

- **천장(확정) 기준만** (2026-10-24 결정). 계획은 최악의 경우 — 모든 목표가 천장에서 나온다 — 로 세운다
- 목표마다 **"천장 전에 나올 확률"을 보조 숫자**로 둔다. 기대값 모드는 넣지 않는다 (평균 소비 비표시 결정과 같은 이유)

### 스택 방식에서 계산이 달라지는 점

- **스택은 두 개를 따로 추적한다.** 픽업은 모집 스택, 특별 픽업·페스는 특별 스택. 같은 시기의 목표라도 서로 돕지 못한다
- **목표의 천장 비용은 직전 스택에 달렸다.** 각 스택의 첫 목표는 지금 스택에서, 확정으로 얻은 뒤의 목표는 0에서 시작한다
- **마일리지는 기간마다 새로.** 같은 기간의 일반·특별·페스가 공유하고 기간이 끝나면 사라진다. 계획 단위는 "기간마다 몇 연"이다 —
  같은 200연도 한 기간에 몰면 티켓 4장(40연), 두 기간에 나누면 적게 받는다
- 무료 모집(`freePulls`)이 스택·마일리지에 쌓이는지는 미확인 → 확인 전에는 계산에 넣지 않고 안내만 한다

## 4. 데이터

### 4-1. 미래시 — 출처와 형식

한국 일정은 일본 순서를 따르지만 고정 간격으로 옮길 수 없다 (미래시 6개월 → 3개월 단축 중, 묶음·순서 변경 있음).

| 정보 | 출처 | 상태 |
|---|---|---|
| 픽업 학생·배너 종류·이벤트 날짜 | 커뮤니티 미래시 (몰루로그, 아카라이브) 두 곳 이상 교차 | `estimated` |
| 확정 날짜 | 한국 공식 업데이트 안내 | `announced` |

`data/ko/schedule.json`의 `recruits[]` — 기간 단위, 배너 여럿:

```
{ id: 'YYYY-MM-DD-슬러그', start, end, status, event?, freePulls?,
  banners: [{ type: banner-types id, students: [students.json id] }],
  sources: [...], note? }
```

- 스택 종류·픽뚫 여부는 `type`에서 파생한다 (저장하지 않는다 — 설계 원칙 1)
- `end`는 출처가 모집 기간을 밝히지 않으면 시작일 + 7일 (한섭 픽업은 1주 운영). 판정에는 시작일이 중요하다
- 두 출처의 날짜가 다르면 `note`에 적는다 (예: 11월 픽업 3건은 아카라이브가 몰루로그보다 1주 이르다)
- 추정 날짜는 화면에서 주 단위로 보인다 — 판정을 바꾸는 것은 날짜보다 순서와 그 사이 수급량이다

`data/ko/students.json` — 미래시에 나오는 학생만 (전체 도감이 아니다, 텍스트만):

```
{ id, gameId, name: { ko, ja }, koNameStatus: official | provisional }
```

- **미출시 학생 이름** (2026-10-24 결정): 한국 공식 표기가 없으면 커뮤니티에서 주로 쓰는 이름 + `provisional` → 화면에 "가칭"과 일본 공식 이름을 함께
- 의상 학생은 한국 공식 표기 방식 "이름(의상)"

### 4-2. 검증 (`validate.py` `check_recruits`)

- 오류: id 중복·형식(시작일로 시작), 날짜 순서, 스택 전환 이전 기간, 공지 기간의 공식 출처, 없는 출처·배너 종류·학생, 한국 미운영 배너, 빈 배너, 추정 뒤의 공지
- 경고: 출처가 하나뿐인 추정 기간, 일본 이름 없는 가칭 학생, 어느 픽업에도 없는 학생
- 운영: 한국 업데이트 안내가 나올 때마다 해당 기간을 `announced`로 바꾸고 뒤따르는 추정을 보정. 커밋 메시지에 출처.
  추정 이력은 따로 저장하지 않고 git 히스토리에 맡긴다 (나중에 "추정이 실제와 얼마나 어긋났나"를 계산할 수 있다)

### 4-3. 저장소

v0.2까지 JSON + PR (2026-10-24 결정). `validate.py`와 CI가 곧 검증 장치다. DB는 플래너 공개 뒤에 다시 본다.

| 입력 | 어디서 | 비고 |

| 목표 학생 | 예정 픽업 목록에서 선택 | 이미 끝난 기간은 숨긴다 (`listRecruits({ from })`) |

| 남겨 둘 청휘석 (선택) | 플래너 | 예상 못 한 픽업 대비 |

## 6. 결과 화면 (모바일 기준 위 → 아래)

1. **판정 요약** — "목표 4명 중 3명 확정 가능" + 가장 중요한 한 줄
2. **기간 목록** — 기간마다 한 줄: 날짜(추정 배지), 내 목표, 행동(N연 / 넘기기), 그 시점 잔고(전 → 후)
3. **목표별 판정** — 확보 가능 / N개 부족 / 불가(이유: 픽뚫 불가인데 천장 못 채움 등) + 천장 전에 나올 확률
4. **대안** — 최대 2개. "2순위를 빼면 3·4순위 확보"
5. **잔고 곡선** — 지출 지점에서 떨어지는 곡선. 넓은 화면은 오른쪽 열

고지: "예상 일정이며 바뀔 수 있어요" + 일정 확인일. 가로 차트를 주인공으로 두지 않는다 — 380px에 몇 달치 주간 픽업이 들어가지 않는다.

디자인: 디자인 문서 10장 "새 화면을 만들 때" — `PageTitle`, 답은 `Panel` `e2` + `tone` + `pulse` + `marks`, 결과판 전환 이름 `vt-result-planner`, `nav.ts` `ready`.
판정 색은 디자인 문서 5-18 표에 행을 더해 정한다.

## 7. 계산 (`src/lib/calc/planner.ts`, 순수 함수)

```
1. 날짜별 청휘석 잔고 (수급 계산 재사용)
2. 우선순위대로 목표에 예산 배정
   - 목표가 속한 기간·스택 종류를 찾는다
   - 천장까지 연차 = 200 − 그 스택의 현재값 (이전 목표를 확정으로 얻었으면 0에서)
   - 같은 기간 목표끼리 연차를 합쳐 마일리지 티켓을 센다 (gemPullsToReach)
   - 기간 시작일의 잔고(그 사이 수급 포함)가 비용 이상이면 확보, 아니면 부족분 기록하고 다음 목표로
3. 대안: 포함/제외 조합 2^N 전수 (목표 8개 = 256가지, 브라우저에서 즉시)
   - 확보 수 최대, 우선순위 가중 합 최대 조합을 각각
```

- 넘긴 픽업에서는 뽑지 않으므로 스택이 그대로 이월된다
- 확률·비용 함수는 `gacha.ts`의 스택 함수를 그대로 쓴다
