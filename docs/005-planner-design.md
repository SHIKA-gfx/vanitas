# 005. 픽업 플래너 설계 (v0.2)

> 작성: 2026-10-24 · 갱신: 2026-10-25 (9장 부족분 메우기) · 상태: 설계 확정, 데이터 초안 검토 중
> 관련: 기획서 3-4, `docs/004`(경쟁 서비스·데이터 출처 정책), 개발 결정 문서 1장 "천장 규칙은 날짜의 함수"·"스택 방식 계산"

## 1. 무엇을 답하는가

> **고른 학생들을 지금 재화와 앞으로의 수급으로, 우선순위대로 몇 명까지 확정으로 데려올 수 있고,
> 그러려면 픽업마다 얼마를 쓰고 얼마를 남겨야 하나.**

답은 세 겹이다.

- **판정**: 목표마다 확보 가능 / N개 부족 / 불가(이유)
- **행동**: 픽업 기간마다 몇 연 / 넘기기, 그 시점 잔고
- **대안**: 무엇을 포기하면 무엇이 되나 (최대 2개)

하지 않는 것

- 학생 성능 평가·추천 — 주관이 크고 커뮤니티 평가글의 영역
- 일정 안내 자체 — 일정은 고르기 위한 재료
- 과금 권유 — 부족분은 청휘석 개수로만 말한다

## 2. 범위 (v0.2)

- **모집 스택 방식만 다룬다.** 플래너는 2026-11-10 전환 뒤에 공개되므로 계획 대상 픽업은 모두 스택 시대다. 포인트 방식·전환일을 가로지르는 계산은 없다
- **목표는 "확정(천장까지)" 하나뿐** (2026-10-24 결정). "반천장까지만"은 v0.2 다음으로 미룬다 —
  그 학생에게는 못 얻는 경우가 최악이지만 뒤의 목표에게는 얻는 경우(스택 초기화)가 최악이라, 안전 계획 하나로 묶을 수 없다
- 학생 한 명당 1장. 중복 획득(신비 해방 등)은 다루지 않는다

## 3. 판정 기준

- **천장(확정) 기준만** (2026-10-24 결정). 계획은 최악의 경우 — 모든 목표가 천장에서 나온다 — 로 세운다
- 목표마다 **"천장 전에 나올 확률"을 보조 숫자**로 둔다. 기대값 모드는 넣지 않는다 (평균 소비 비표시 결정과 같은 이유)

### 스택 방식에서 계산이 달라지는 점

- **스택은 두 개를 따로 추적한다.** 픽업은 모집 스택, 특별 픽업·페스는 특별 스택. 같은 시기의 목표라도 서로 돕지 못한다
- **목표의 천장 비용은 직전 스택에 달렸다.** 각 스택의 첫 목표는 지금 스택에서, 확정으로 얻은 뒤의 목표는 0에서 시작한다
- **마일리지는 기간마다 새로.** 같은 기간의 일반·특별·페스가 공유하고 기간이 끝나면 사라진다. 계획 단위는 "기간마다 몇 연"이다 —
  같은 200연도 한 기간에 몰면 티켓 4장(40연), 두 기간에 나누면 적게 받는다
- 무료 모집(`freePulls`)이 스택·마일리지에 쌓이는지는 미확인 → 확인 전에는 계산에 넣지 않고 안내만 한다

## 4. 데이터

### 4-1. 미래시 — 출처와 형식

한국 일정은 일본 순서를 따르지만 고정 간격으로 옮길 수 없다 (미래시 6개월 → 3개월 단축 중, 묶음·순서 변경 있음).

| 정보 | 출처 | 상태 |
|---|---|---|
| 픽업 학생·배너 종류·이벤트 날짜 | 커뮤니티 미래시 (몰루로그, 아카라이브) 두 곳 이상 교차 | `estimated` |
| 확정 날짜 | 한국 공식 업데이트 안내 | `announced` |

`data/ko/schedule.json`의 `recruits[]` — 기간 단위, 배너 여럿:

```
{ id: 'YYYY-MM-DD-슬러그', start, end, status, event?, freePulls?,
  banners: [{ type: banner-types id, students: [students.json id] }],
  sources: [...], note? }
```

- 스택 종류·픽뚫 여부는 `type`에서 파생한다 (저장하지 않는다 — 설계 원칙 1)
- `end`는 출처가 모집 기간을 밝히지 않으면 시작일 + 7일 (한섭 픽업은 1주 운영). 뽑는 날을 기간 마지막 날로 보므로 `end`가 판정에 쓰인다
- 두 출처의 날짜가 다르면 `note`에 적는다 (예: 11월 픽업 3건은 아카라이브가 몰루로그보다 1주 이르다)
- 추정 날짜는 화면에서 주 단위로 보인다 — 판정을 바꾸는 것은 날짜보다 순서와 그 사이 수급량이다

`data/ko/students.json` — 미래시에 나오는 학생만 (전체 도감이 아니다, 텍스트만):

```
{ id, gameId, name: { ko, ja }, koNameStatus: official | provisional }
```

- **미출시 학생 이름** (2026-10-24 결정): 한국 공식 표기가 없으면 커뮤니티에서 주로 쓰는 이름 + `provisional` → 화면에 "가칭"과 일본 공식 이름을 함께
- 의상 학생은 한국 공식 표기 방식 "이름(의상)"

### 4-2. 검증 (`validate.py` `check_recruits`)

- 오류: id 중복·형식(시작일로 시작), 날짜 순서, 스택 전환 이전 기간, 공지 기간의 공식 출처, 없는 출처·배너 종류·학생, 한국 미운영 배너, 빈 배너, 추정 뒤의 공지
- 경고: 출처가 하나뿐인 추정 기간, 일본 이름 없는 가칭 학생, 어느 픽업에도 없는 학생
- 운영: 한국 업데이트 안내가 나올 때마다 해당 기간을 `announced`로 바꾸고 뒤따르는 추정을 보정. 커밋 메시지에 출처.
  추정 이력은 따로 저장하지 않고 git 히스토리에 맡긴다 (나중에 "추정이 실제와 얼마나 어긋났나"를 계산할 수 있다)

### 4-3. 저장소

v0.2까지 JSON + PR (2026-10-24 결정). `validate.py`와 CI가 곧 검증 장치다. DB는 플래너 공개 뒤에 다시 본다.

## 5. 사용자 입력

| 입력 | 어디서 | 비고 |
|---|---|---|
| 청휘석·티켓 | 공유 값 (`UserState`) | |
| 모집 스택·특별 스택 | 공유 값 | 천장·확률 계산기와 같은 값 |
| 수급 조건 | **수급 계산기 입력을 그대로** (2026-10-24 결정) | 플래너에는 요약 한 줄 + "수급 계산기에서 바꾸기". 기본값·검사·공유 이름은 `income-settings.ts` 하나를 두 화면이 쓴다. **공유 링크에는 보낸 사람의 수급 조건이 실린다** (2026-10-25 결정) — 이름은 수급 계산기와 같고(`ps`·`inc`·`tac`·`tier`·`ev`·`sub`), 종료 날짜(`d`)는 싣지 않는다. 받은 사람이 값을 고쳐 저장하면 수급 계산기 값도 그 값이 된다 (종료 날짜는 받은 사람 것) |
| 목표 학생 | 예정 픽업 목록에서 선택 | 이미 끝난 기간은 숨긴다 (`listRecruits({ from })`) |
| 우선순위 | 순서 정렬 | 모바일은 위/아래 버튼, 끌기는 보조 |
| 남겨 둘 청휘석 (선택) | 플래너 | 예상 못 한 픽업 대비 |

## 6. 결과 화면 (모바일 기준 위 → 아래)

1. **판정 요약** — "목표 4명 중 3명 확정 가능" + 가장 중요한 한 줄
2. **기간 목록** — 기간마다 한 줄: 날짜(추정 배지), 내 목표, 행동(N연 / 넘기기), 그 시점 잔고(전 → 후)
3. **목표별 판정** — 확보 가능 / N개 부족 / 불가(이유: 픽뚫 불가인데 천장 못 채움 등) + 천장 전에 나올 확률
4. **대안** — 최대 2개. "2순위를 빼면 3·4순위 확보"
5. **잔고 곡선** — 지출 지점에서 떨어지는 곡선. 넓은 화면은 오른쪽 열

고지: "예상 일정이며 바뀔 수 있어요" + 일정 확인일. 가로 차트를 주인공으로 두지 않는다 — 380px에 몇 달치 주간 픽업이 들어가지 않는다.

구현 (2026-10-25, `src/routes/planner/`): `PickupPicker`(예정 픽업, 누르기 단추 `aria-pressed`) · `PlannerResult`(결과판 + 내 목표 + 대안 + 안내) · `PeriodPlan`(기간별 계획) · 잔고 곡선은 수급 계산기의 `BalanceCurve`.
목표 이름은 `기간 id~학생 id` (`target-key.ts`) — 저장값과 공유 링크 `tg=`가 쓴다. 끝난 기간의 목표도 저장값으로 받아 "기간이 끝났어요"로 보여준다.

디자인: 디자인 문서 10장 "새 화면을 만들 때" — `PageTitle`, 답은 `Panel` `e2` + `tone` + `pulse` + `marks`, 결과판 전환 이름 `vt-result-planner`, `nav.ts` `ready`.
판정 색은 디자인 문서 5-18 표에 행을 더해 정한다.

## 7. 계산 (`src/lib/calc/planner.ts`, 순수 함수 / `planner-adapter.ts`)

어댑터가 날짜를 "오늘 = 0"인 일 수로 바꾸고, 수급 계산기 입력으로 `calculateIncome`을 돌려 날짜별 잔고(`gemsByDay`)와 받은 티켓을 만든다.
`planPickups`는 그 숫자만 안다.

1. **한 묶음 평가** (`evaluateSet`) — 목표 묶음을 모두 천장에서 얻는 최악의 경우를 날짜순으로 따라간다
   - 목표의 시작 스택: 종류의 첫 목표는 지금 스택, 그 뒤는 0. 같은 기간에 같은 종류가 둘이면 우선순위가 높은 쪽이 먼저
   - 기간의 연차를 합쳐 마일리지 티켓을 센다 (`spendInPeriod`). **받은 티켓(기간제) → 가진 티켓 → 청휘석** 순으로 쓴다.
     지금 진행 중인 기간만 현재 마일리지에서, 나머지는 0에서
   - **뽑는 날은 기간의 마지막 날** — 그 기간 동안 받는 수급까지 쓸 수 있다 (4-1의 "시작일 기준"에서 바꿈, 2026-10-24)
   - 청휘석을 쓰면 그 뒤 모든 날의 잔고가 줄어든다. 그래서 "쓰는 날 이후 가장 낮은 잔고"(AP 구매로 잔고가 줄어드는 날 포함)와 비교한다.
     모자란 양(`deficit`)이 0이면 가능
2. **우선순위 계획** — 1순위부터 하나씩 넣어 보고, 넣어도 묶음 전체가 가능할 때만 남긴다. 뒤 순위가 앞 순위를 밀어내지 않는다
3. **목표별 결과** — 계획에 든 목표는 `secured`, 아니면 **"앞 순위 계획에 이 목표를 더하면"**의 스택 시작값과 모자란 청휘석으로 `short`.
   끝난 기간·없는 기간은 `unavailable` (저장·공유된 목표가 낡았을 때)
   - 2026-10-25 바꿈 (전: "완성된 계획에 이 목표를 더하면"): 계획에 든 **뒤 순위** 목표의 비용은 섞지 않는다.
     뒤 순위는 앞 순위를 밀어내지 않으므로, 모자란 만큼 더 받으면 이 목표가 계획에 들고 뒤 순위가 다시 맞춰진다 — 2번과 같은 묶음이다.
     전에는 부족분 메우기 도중 뒤 순위가 먼저 확보되면 앞 순위의 부족이 그 비용만큼 튀었다 (실데이터 예: 2,942 → 17,342)
   - 예 (사용자 예시): 시작 36,000, 픽업 사이마다 +6,000, 천장 24,000, 1·2·3순위가 날짜 순서대로 →
     1·3순위 확보, 2순위는 픽업 때 18,000뿐이라 **6,000 부족** (전 기준은 3순위 비용까지 더해 24,000).
     2순위 픽업까지 6,000을 더 받으면 2순위가 확보되고 3순위가 18,000 부족해진다 — 이것은 9장의 부족분 메우기가 알린다
4. **대안** — 포함/제외 조합 전수 (목표 12개까지, 2^12 = 4,096). 계획보다 많이 확보하는 조합을 확보 수, 그다음 우선순위 순으로 최대 2개.
   우선순위는 비트 가중치로 비교한다 — 1순위 하나가 아래 순위 전부보다 무겁다
5. **날짜별 잔고** — `gemsByDay`에서 계획의 지출을 뺀 값 (결과 화면의 잔고 곡선)

- 넘긴 픽업에서는 뽑지 않으므로 스택이 그대로 이월된다
- 천장 전 확률은 `gacha.ts`의 `chargeProbAtLeastOne`(199연까지)
- 무료 모집(`freePulls`)은 계산에 넣지 않고 `freePullsIgnored`로 알린다 (스택·마일리지 적립 미확인)
- 검증: 손으로 센 기준값(19,200 / 10,800, 이월, 같은 기간 마일리지 공유, AP 구매로 줄어드는 날, 남겨 둘 청휘석) +
  무작위 60회 — 계획만 다시 넣으면 전부 확보되는지, 대안이 실제로 가능한지, 계획 잔고가 0 밑으로 가지 않는지

| 2026-10-25 | 부족분 메우기의 정액 상품은 그 픽업까지 필요한 횟수까지만, 확보되면 가장 적은 횟수로 |
| 2026-10-25 | 부족분 메우기는 우선순위를 그대로 두고, 밀려나는 뒤 순위 목표와 그 부족분을 함께 알린다 |
| 2026-10-25 | 전술대회 순위별 일일 보상(rankRewards) 추가 — "한 단계 위"용 (나무위키, 사용자 확인) |

## 9. 부족분 메우기 (2026-10-25)

> 질문: **"부족"인 목표를 그 기간까지 데려오려면 수급 조건을 어떻게 바꾸면 되나.**
> 계획 판 "부족" 줄 안의 접기 "메우는 방법". 계산 `src/lib/calc/planner-fill.ts`, 화면 `src/routes/planner/FillPlan.svelte`

1장의 "과금 권유를 하지 않는다"는 그대로다. 바꿀 수 있는 수급 조건과 그 효과를 **사실로만** 늘어놓고, 무료 방법을 먼저 다 본다.

### 9-1. 바꾸는 방법과 폭

| 종류 | 방법 | 폭 |
|---|---|---|
| 무료 | 받는 보상(수급 계산기 체크) | 켜기. 이벤트를 켤 때 참여도가 "미참여"면 한 단계 올린 것까지 한 방법 |
| 무료 | 총력전 최종 등급 | 한 단계 위 (브론즈 → 실버 …) |
| 무료 | 전술대회 일일 보상 | 한 단계 위 — 지금 금액보다 많은 첫 순위 금액 (`rankRewards`, 예: 20 → 25개 101~200위) |
| 무료 | 이벤트 참여도 | 한 단계 위 (미참여 → 절반 → 완주) |
| 무료 | 하루 AP 구매 | N회 → 0회 |
| 과금 | 정액 상품(월정액·반정액) | 그 픽업이 끝날 때까지 필요한 구매 횟수까지. 그 단계에서 확보되면 확보되는 가장 적은 횟수로 줄인다 |

- 한 방법은 한 번만 쓴다 (등급·순위·참여도도 한 단계만)
- 청휘석 직접 구매는 다루지 않는다 (가격·수량 데이터 없음)
- 전술대회 순위별 보상은 `income-sources.json` `tactical-tournament.rankRewards` (출처 33 나무위키, 1~3구간은 사용자 확인).
  계산기 입력은 여전히 금액 하나라, 금액이 표의 사이에 있으면 그보다 많은 첫 구간으로 올린다

### 9-2. 계산

1. 조건 하나를 바꿔 **플래너를 통째로 다시 돌린다** — 수급 차이를 더하지 않는다. 우선순위·스택 이월·다른 목표와의 관계가 그대로 반영된다
2. 매 단계, 남은 방법 중 **효과가 가장 큰 것**을 하나 골라 쌓는다. 효과는 그 목표의 픽업에 더 쓸 수 있게 되는 청휘석 —
   뽑는 날 이후 가장 낮은 잔고의 증가(7장의 비교 값) + 그날까지 더 받는 10회 모집 티켓(1장 = 10연 = 1,200개로 환산). 효과가 0인 방법은 고르지 않는다
3. 그 목표가 확보되면 멈춘다. 무료를 다 써도 모자라면 정액 상품을 같은 방식으로 더하고, 그래도 모자라면 남은 부족분을 알린다
4. 단계마다 남은 부족(7장 3번의 부족 청휘석), **함께 확보되는 목표**, 이 목표가 확보되며 **밀려나는 뒤 순위 목표와 그 부족분**
5. 다시 돌릴 때는 대안 전수 탐색을 끄고(`planPickups(input, { alternatives: false })`), 같은 수급 조건의 수급 계산은 한 번만 한다
   (`createShortfallFiller(query)`가 목표끼리 나눠 쓴다, `planFromData(query, { income })`). 접기를 펼칠 때만 계산한다 — 목표 하나에 12~60ms(노드)

**"+N개"의 뜻**: 그 픽업에 더 쓸 수 있게 되는 청휘석. 계획은 마지막 픽업까지 잔고가 0 밑으로 내려가지 않아야 하므로,
AP 구매 줄이기는 11월 픽업에도 마지막 픽업까지 아끼는 양(예: 3회 → 0회 +10,260)으로 나온다. 접기 아래 안내 한 줄이 이것을 말한다

**우선순위는 그대로 둔다** (사용자 예시): 시작 36,000, 픽업 사이마다 +6,000, 천장 24,000, 1·2·3순위가 날짜 순서대로면
2순위는 픽업 때 18,000뿐이라 넘기기, 3순위는 확보. 2순위의 메우는 방법은 2순위 픽업까지 6,000개를 더 모으는 방법이고,
그러면 "대신 부족: 3순위 · 청휘석 18,000개"를 함께 보여준다. 3순위를 지킬지는 사용자가 정한다 (우선순위를 바꾸면 계획이 바뀐다)

### 9-3. 화면

- 계획 판(기간별 계획)의 "부족" 줄 안에, 부족 목표마다 `<details>` 접기 "메우는 방법" (한 줄에 여럿이면 "리오 메우는 방법")
- 단계: 바꾸는 조건(수급 계산기에서 보는 이름) + 오른쪽 "+N개"(티켓 보상은 "+10회 티켓 N장") / 남은 부족 N개.
  단계는 쌓이므로 왼쪽 세로 선으로 잇는다. 확보되는 단계에 "확보" 배지 + "여기까지 바꾸면 확보돼요", 다 바꿔도 모자라면 "부족" 배지 + "다 바꿔도 청휘석 N개 부족해요"
- 과금 단계는 "과금" 배지(테두리)와 사실만. 가격 비교·추천 문장 없음
- 아래에 안내 한 줄과 "수급 계산기에서 바꾸기" (보유 재화 요약 줄의 링크와 같은 곳)
- 판정 색·배지 문법은 디자인 문서 5-18·5-20 그대로
