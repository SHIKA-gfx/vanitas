## 1. 무엇을 하는가

v0.3은 두 갈래다. 기말 발표(11월 말) 전에는 ⑥을 끝내고, ⑦은 시간이 남으면 하고 아니면 발표 뒤에 한다 (2026-11-14 결정).
→ 2026-11-15: 발표 날짜가 아직 공지되지 않아, ⑦은 **발표 날짜를 기준으로 두지 않고 끝까지 만든다** (10-6의 마감선을 뺐다).
릴리스는 나눈다 (2026-11-15 결정): **⑥만으로 `v0.3.0`**을 내고, ⑦은 끝나는 대로 `v0.3.1` — 발표에서 로그인 저장을 릴리스된 기능으로 보이고, ⑦이 늦어져도 발표에 지장이 없게.

| 단계 | 내용 | 발표 전 | 릴리스 |
|---|---|---|---|
| ⑥ 로그인 저장 | 구글·카카오로 로그인하면 입력값을 계정(DB)에도 저장한다. 브라우저 저장은 그대로 두고, 계정 값과 맞춘다 | **한다** (완료) | `v0.3.0` |
| ⑦ 목표 종류 | 플래너 목표에 "반천장까지"(스택 100까지), "N연까지"(정한 연 수만큼, 확률로만)를 더한다 — 10장 | 끝까지 만든다 (발표 날짜와 관계없이) | `v0.3.1` |

바꾸지 않는 것: 로그인 없이도 지금처럼 쓴다(브라우저 저장). 공유 링크·백업 링크는 그대로다 — 계정과 관계없이 링크에 값이 담긴다.

## 2. 결정 (2026-11-14)

| 무엇 | 결정 | 이유 |
|---|---|---|
| 로그인 수단 | **구글 + 카카오** (이메일·비밀번호 가입은 막는다 — 관리자만) | 둘 다 Supabase가 기본 제공한다. 네이버는 기본 제공이 아니다 — "커스텀 OAuth 제공자"(2026-04, 무료 3개)로 붙여도 사용자 정보가 `response` 안에 한 겹 싸여 와서 중계 함수가 필요하고, 모두에게 열려면 네이버 검수 승인을 기다려야 한다 |
| 저장 단위 | 사용자마다 한 행에 저장 파일(`vanitas:v1`의 `{ version, sections }`)을 통째로 (`jsonb`) | 006 8장의 계획 그대로. 열로 나누지 않으므로 저장 형식이 바뀌어도 DB를 고치지 않는다. 읽을 때는 지금처럼 `parseSaveFile`·`persistSection`의 검사를 거친다 |
| 기기 값과 계정 값이 다를 때 | **한 번 묻는다** ("이 기기 값 / 계정 값"), 그 뒤로는 자동 저장 | 몰래 덮으면 한쪽 입력이 사라진다 |
| 확률 목표 | **연 수를 정한다** (예: 50연까지만) | ⑦에서 — 설계는 10장 (2026-11-15) |

### 화면·카카오 (2026-11-14 결정)

- **H. 로그인 단추 자리**: 데스크톱은 왼쪽 목록 아래 "백업 링크" 바로 위(모든 화면), 모바일은 홈 화면의 같은 자리. 로그인하면 그 자리가 계정 단추(사람 + 확인 표시 선 아이콘, 2026-11-15 이름 첫 글자에서 바꿈 — 다른 아이콘과 같은 선 모양으로)로 바뀌고 누르면 계정 창(로그인한 제공자·저장 상태·로그아웃·계정 삭제)
- **I. 카카오 이메일**: 처음에는 "받지 않는다"로 정했으나 **바꿨다** — Supabase Auth의 카카오 제공자는 설정과 상관없이 `account_email`·`profile_image`·`profile_nickname`을 늘 요청한다(`supabase/auth` `internal/api/provider/kakao.go`, 2026-11-13). 카카오는 설정하지 않은 동의 항목을 요청받으면 KOE205로 막는다.
  → **개인 개발자 비즈 앱으로 바꾸고 이메일은 선택 동의**, 프로필 사진도 선택 동의로 켠다. 사용자가 이메일 제공을 거절해도 로그인되게 Supabase 카카오 설정의 "Allow users without an email"을 켠다. 우리는 이메일을 쓰지 않는다(저장값은 사용자 번호로 찾는다)
- **J. 로그아웃할 때 이 기기 값**: **그대로 둔다** (로그인 전처럼 이 기기에서 계속 쓴다). 계정 삭제 때도 계정의 값만 지우고 이 기기 값은 그대로 둔다

## 3. DB (`supabase/migrations/20261115000000_user_saves.sql`)

### 3-1. 표 `user_saves`

| 열 | 형 | 설명 |
|---|---|---|
| `user_id` | uuid PK → `auth.users` (삭제 시 같이 삭제) | 사용자 |
| `data` | jsonb | 저장 파일 `{ version, sections }`. 객체만, 64KB까지 (지금 저장값은 수 KB) |
| `updated_at` | timestamptz | 판. 저장할 때마다 바뀐다 — 다른 기기의 저장을 알아채는 데 쓴다 |

- **보안 규칙**: 로그인한 사람(`authenticated`)이 **자기 행만** 읽고·쓰고·지운다 (`user_id = auth.uid()`). 방문자(`anon`)는 아무것도 못 한다. 관리자도 남의 저장값을 보지 않는다
- 게임 데이터 표의 쓰기는 지금처럼 `is_admin()`이 막는다(006 5장) — 로그인을 열어 누구나 `authenticated`가 되어도 바뀌지 않는다. ⑥-2 전에 권한을 한 번 더 점검한다(6-3)

### 3-2. 함수

| 함수 | 하는 일 |
|---|---|
| `save_my_data(data, 먼저 읽은 판)` | 판이 같을 때만 저장하고 새 판을 돌려준다. 처음 저장이면 판 없이. 다르면 `P0001`(다른 기기에서 먼저 저장) — 화면이 묻는다. security invoker |
| `delete_my_account()` | 자기 계정을 지운다(저장값도 함께). 관리자 계정은 거부. security definer — `auth.users`를 지울 권한이 필요해서. 권한 확인은 `auth.uid()` 하나로 |
| `hook_before_user_created(event)` | Supabase Auth의 "Before User Created" 훅. **구글·카카오가 아닌 새 계정은 거부**한다 — 가입을 열어도 이메일·비밀번호 가입은 막힌다. Auth만 부른다(`supabase_auth_admin`) |

- 훅은 대시보드 Authentication → Hooks에서 고른다. 무료 플랜에서 되는지 적용할 때 확인한다 (안 되면 "Confirm email"을 켜 두고, 이메일 가입 계정은 권한이 없으니 그대로 둔다)
- 새 관리자를 대시보드에서 만들 때는 훅이 막는다 — 잠깐 끄고 만든 뒤 다시 켠다
- 로컬 시험(2026-11-14, Postgres 16 + 가짜 `auth`): 방문자 거부, 첫 저장·판으로 다시 저장, 옛 판·처음인 척 저장은 `P0001`, 객체 아님·64KB 넘음 거부, 남의 행 쓰기·읽기 불가, 손님의 게임 데이터 쓰기 거부(기존 규칙), 관리자 계정 삭제 거부·손님 계정 삭제 때 저장값 함께 삭제, 훅은 `email`·제공자 없음 거부, `google`·`kakao` 통과, 로그인한 사람은 훅을 부를 수 없음

## 4. 맞추기 규칙

이 기기에 `vanitas:sync` = `{ userId, syncedAt(마지막으로 맞춘 판), syncedHash(그때 저장 파일의 지문) }`을 둔다 (`src/lib/sync.ts`).
저장값(`vanitas:v1`)과 따로 — 백업 링크·공유 링크에 실리지 않는다. **"이 기기에서 고침"(dirty)은 지금 파일의 지문 ≠ syncedHash**로 정한다 —
로그아웃한 동안 고친 것도 다음 로그인 때 알아채고, 받은 값을 화면이 다시 써도(같은 값) 고친 것으로 치지 않는다 (처음 설계의 dirty 표시를 바꿈, ⑥-3).

| 때 | 계정에 행 | 이 기기 | 하는 일 |
|---|---|---|---|
| 언제든 | 없음 | — | 이 기기 값을 올린다 |
| | 있음 | 값이 같음(지문) | 그대로 (그 판을 맞춘 판으로) |
| 처음 로그인 (이 기기에 이 사람과 맞춘 기록 없음) | 있음 | 다름 | **묻는다** (이 기기 값 / 계정 값) |
| 다시 열 때 | 판 = syncedAt | 고침 | 올린다 |
| | 판 = syncedAt | 안 고침 | 그대로 |
| | 판 ≠ syncedAt | 안 고침 | 계정 값을 받는다 |
| | 판 ≠ syncedAt | 고침 | **묻는다** |
| 고칠 때 | | | 브라우저에 저장(지금처럼) → 2초 모아서 지문이 다르면 `save_my_data`. 판이 다르면(P0001) 다시 읽어 위 표대로 — 몰래 덮지 않는다 |

- 처음 설계의 "이 기기가 비었으면(기본값) 계정 값을 받는다"는 빼고 **묻는다**로 합쳤다 — 기본값인지를 계산기마다 따로 알아야 해서. 묻기 창에 두 값의 요약(보유 청휘석, 플래너 목표 수, 계정 저장 시각)이 있어 새 기기는 "계정 값 쓰기"를 고르면 된다
- 계정 값을 받으면 `SavedStore.importFile(…, { fromAccount })` → `generation`이 올라 **열려 있는 계산기 화면도 자기 묶음을 다시 읽는다** (예전 백업 불러오기는 다른 화면을 열 때 읽었다)
- 공유 링크를 보는 동안(저장 멈춤)에는 맞추기를 끈다. 계정 창에 "공유 링크를 보는 동안에는 계정에 저장하지 않아요"
- 연결이 끊기면 이 기기에만 저장해 두고 "다시 연결되면 계정에도 올려요". 다시 연결(online)·화면으로 돌아옴(visibilitychange) 때 다시 시도
- 묻기 창의 "나중에 고르기": 고를 때까지 올리지 않는다. 계정 창의 "고르기"나 다음에 열 때 다시 묻는다

## 5. 화면

- **로그인 단추**(H): "로그인" → 고르기(구글 / 카카오) → 제공자 화면 → `/ko/auth/callback`으로 돌아와 원래 화면으로
- **계정 칸**: 로그인한 제공자, "계정에 저장됨 · 방금" 같은 상태, 로그아웃, 계정 삭제(한 번 더 묻고)
- **묻기 창**(4장): 두 값의 요약(목표 학생 수, 보유 청휘석, 마지막 저장 시각)을 나란히 보여 주고 고르게 한다
- **개인정보 처리방침** `/ko/privacy`: 7장. 정보와 출처 페이지·로그인 고르기 창에서 링크
- 문구 바꾸기: 정보와 출처의 저장 안내(`about_storage_body`), README "로그인 없이 자동 저장" — "로그인하지 않으면 이 기기에만, 로그인하면 계정에도 저장돼요"
- **번들**: supabase-js는 지금 `/admin`에만 있다. 방문자 화면은 로그인 단추를 누르거나 이 기기에 로그인 기록이 있을 때만 불러온다 — 로그인하지 않는 방문자의 첫 화면은 그대로 가볍게. Supabase 연결은 `/admin`과 한 곳(`$lib/supabase.ts`)으로 모은다

### 5-1. ⑥-2에서 만든 것 (2026-11-15)

- `$lib/supabase.ts`: 연결 하나. 관리자 화면은 바로(`supabaseWith`), 방문자 화면은 필요할 때(`loadSupabase`) — 로그인 기록(`sb-…-auth-token`)이 없으면 첫 화면에서 supabase-js를 불러오지 않는다 (시험으로 확인). PKCE 흐름
- `$lib/account.ts`(순수 함수·테스트)와 `$lib/account.svelte.ts`(상태): 시작, 로그인(돌아갈 화면을 탭에 기억), 돌아온 code를 세션으로, 로그아웃(관리자 표시도 지운다), 계정 삭제(`delete_my_account` 뒤 이 기기의 로그인 정보만 지운다)
- `AccountButton`: 왼쪽 목록(모든 화면)·모바일 홈의 "로그인 / 계정" 단추와 `<dialog>` 창. 제공자 단추는 글자만 (공식 단추 이미지는 받아 오면 바꾼다)
- `/ko/auth/callback`: code → 세션 → 시작한 화면으로(사이트 안의 경로만). 취소·가입 막힘·훅 거부·실패를 문장으로. 검색 제외(X-Robots-Tag)
- `/ko/privacy`: 개인정보 처리방침. 사이트맵에 더함
- **시험 공개**: `ACCOUNTS_OPEN = false` 동안 단추는 주소에 `?accounts=preview`를 붙인 브라우저에서만 보인다(`?accounts=off`로 끈다). 로그인한 기기에는 늘 보인다(로그아웃하게)
- 모바일 홈의 맨 아래 묶음(관리자·계정·백업)이 375×667에서 타일과 겹쳐, 모바일만 흐름에 두고 아래에 붙였다
- (2026-11-15 운영 시험 뒤) 구글로 로그인했는데 "로그인했어요"로 나왔다 — 관리자 계정(이메일)과 같은 Gmail이라 Supabase가 구글 로그인을 관리자 계정에 **이었고**, `app_metadata.provider`는 처음 만든 수단(`email`)이다. → 이 기기에서 고른 수단(`vanitas:auth-provider`, 관리자 화면의 비밀번호 로그인은 `email`)이 그 계정에 붙어 있으면 그것, 아니면 연결된 수단(identities) 중 마지막 로그인, 아니면 `app_metadata`. 이메일 로그인은 "이메일로 로그인했어요"
  - 이어진 계정이라 구글로 로그인해도 관리자다(같은 사용자). 계정 삭제는 관리자라 거부된다
- 계정 단추의 아이콘을 남색 원 + 흰 이름 첫 글자에서 **사람 + 확인 표시 선 아이콘**으로 (다른 단추처럼 선만, 2026-11-15)
- 시험 (로컬, 가짜 OAuth 게이트웨이 + Postgres): 플래그 없으면 단추 없음, 첫 화면에 supabase-js 없음, Google·카카오 로그인 → 시작한 화면으로, 새로 고침 뒤 유지, 플래그 off여도 로그인 중이면 보임, 로그아웃, 계정 삭제(저장값 함께)·관리자 계정 삭제 거부, 취소·가입 막힘·훅 거부 문장, 관리자 로그인 그대로

### 5-2. ⑥-3에서 만든 것 (2026-11-15)

- `$lib/sync.ts`(순수 함수·테스트): 맞춘 기록, 지문(키 순서와 상관없는 FNV-1a), `decideOnStart`(4장 표), 묻기 창 요약
- `$lib/sync.svelte.ts`: 시작·멈춤·잊기(계정 삭제), 2초 모아 올리기, 판 충돌 → 다시 읽기, 오프라인·재시도, 고르기·나중에
- `SavedStore`: `onLocalWrite`(이 기기에 저장할 때 알림), `generation`(통째로 바뀜 → 화면이 다시 읽음), `importFile(file, { fromAccount })`

## 10. ⑦ 목표 종류 (설계, 2026-11-15)

지금 플래너의 목표는 "확정(천장까지)" 하나다 (`docs/005` 2·3장). 목표마다 종류를 골라, 천장까지 가지 않고 **정한 만큼만 쓰고 확률로 노리는** 목표를 더한다.

### 10-1. 종류

| 종류 | 저장 값 | 계획에 넣는 연 수 | 결과 (화면 이름) |
|---|---|---|---|
| 확정 (기본) | 적지 않는다 | 천장까지: `천장 − 시작 스택` | 확보 / 부족 + 천장 전에 나올 확률 |
| 반천장까지 | `"half"` | 반천장까지: `반천장 − 시작 스택` | **도전** / 부족 + 반천장까지 나올 확률 |
| N연까지 | `"<N>"` (예: `"50"`) | N | **도전** / 부족 + N연 안에 나올 확률 |

- 규칙 값은 코드에 두지 않고 `game-config` `chargeSystem`에서 읽는다: 반천장 `softPity.count` 100(★3 확정, 픽업 `pickupChance` 50%), 천장 `hardPity.count` 200 — 모두 `verified` (출처 30·35, `docs/005` 10-3)
- 1연에 픽업 학생이 나올 확률은 배너 종류의 픽업 ★3 그룹(`banner-types.json`, 지금 0.7%). **픽업 모집은 확인, 특별 픽업·페스는 `verified: false`** → 그 배너의 확률은 "추정 확률"로 보인다 (10-3)
- 예 (스택 0, 0.7%, 1연 120개 `recruitCost.single`): 확정 200연 24,000개 · 100% / 반천장까지 100연 12,000개 · 약 75% / 50연까지 6,000개 · 약 30% (티켓·마일리지 티켓을 쓰기 전 청휘석)

### 10-2. 계산 (`planner.ts` · `planner-adapter.ts`)

**가정**: 확률 목표는 **정한 연 수를 다 쓰고, 마지막 연에 나와 스택 0**이 된다고 본다.

- 청휘석은 다 쓰는 쪽이, 같은 종류의 다음 목표는 0에서 시작하는 쪽이 가장 불리하다 — 둘 다 최악으로 잡는다. 지금 확정 목표와 같은 "최악의 경우" 기준이고, `evaluateSet`의 스택 처리(`stacks[type] = 0`)를 그대로 쓴다
- `docs/005` 2장이 반천장을 미룬 이유("그 학생에게는 못 얻는 경우가, 뒤 목표에게는 얻는 경우가 최악")를 이렇게 푼다: **청휘석과 스택은 남에게 최악으로, 그 목표 자신의 결과만 확률로** 말한다
- 하지 않는 것: "못 뽑아서 스택이 이월된다"고 보는 계획 — 다음 목표의 비용이 줄어드는 낙관적 계획이 된다

**쓰는 연 수**는 지금처럼 `evaluateSet`이 날짜순으로 정한 시작 스택(종류의 첫 목표는 지금 스택, 그 뒤는 0)에서 묶음마다 다시 정한다.

| 경우 | 쓰는 연 수 | 스택 | 결과 |
|---|---|---|---|
| 확정 | `천장 − 시작` | 0 | 확보 / 부족 (지금 그대로) |
| 반천장까지, 시작 < 반천장 | `반천장 − 시작` | 0 | 도전 / 부족 |
| **반천장까지, 시작 ≥ 반천장** | 0 — 계획에 넣지 않는다 | 그대로 이월 (넘기기와 같다) | 불가 `half_passed` + "반천장을 이미 지났어요. 확정이나 N연으로 바꿔 주세요" |
| N연까지, N < `천장 − 시작` | N | 0 | 도전 / 부족 |
| **N연까지, N ≥ `천장 − 시작`** | `천장 − 시작` | 0 | 확정과 같다 — 확보 / 부족. 고른 종류(N)는 그대로 저장 |

- 시작 스택은 같은 종류의 앞 목표가 계획에 드는지에 따라 달라서, 고를 때 막지 않고 결과로 알린다. `half_passed`는 사실상 그 종류의 첫 목표가 지금 스택(입력값)을 받을 때만 생긴다
- **반천장을 지난 목표는 미뤘다가 다시 넣어 본다** (⑦-2에서 더함): 우선순위 계획을 세우는 중에 그때의 계획으로는 반천장을 지났어도,
  뒤 순위의 **앞 날짜** 같은 종류 목표가 계획에 들면 스택이 0이 되어 반천장까지 도전할 수 있다 (예: 지금 스택 120, 1순위 12월 반천장까지 · 2순위 11월 확정 → 11월에 천장으로 얻고 12월은 0에서 100연).
  그래서 계획을 다 세운 뒤 그 목표들을 둔 채로 한 번 더 넣어 보고, 그래도 반천장을 지났을 때만 `half_passed`. 그 목표 덕분에 도전할 수 있는 것이므로 그 목표를 밀어내지 않는다
- 확률: `chargeProbAtLeastOne(1연 확률, 시작 스택, 쓰는 연 수, rule)` — 연 수가 반천장을 지나면 50% 분기가 들어간다 (반천장까지 목표는 마지막 연이 반천장). 확정 목표의 "천장 전에 나올 확률"(199연까지)은 그대로
- 결과(`TargetOutcome`): `secured`·`short`·`unavailable`에 **`attempt`**(확률 목표가 계획에 듦, 화면 "도전")를 더하고, `unavailable.reason`에 `half_passed`. 목표마다 쓰는 연 수와 그 안의 확률을 싣는다
- 우선순위 계획·부족 청휘석·대안은 지금 규칙 그대로 — 비용만 바뀐다. `half_passed` 목표는 우선순위 계획에도 대안의 "더 많이 데려오는" 개수에도 넣지 않는다. 확보 수와 도전 수는 나눠 센다(`securedCount`·`attemptCount`)
- 부족분 메우기(`planner-fill.ts`): 부족한 확률 목표도 같은 방식 — 멈추는 조건이 "확보"에서 **"계획에 듦"**(확보 또는 도전)으로
- **픽업 학생이 여럿인 배너**: 지금 데이터 `2027-02-09-start-your-engines`(2명)·`2027-02-23-art-for-someone`(3명). 반천장 50%가 "픽업 중 하나"인지, 특정 학생의 확률이 얼마인지 공지로 확인하지 못했다(**검증 필요**) → 그 배너의 목표는 **확정만** 고른다. 어댑터가 배너의 학생 수로 정한다(`planner.ts`는 배너를 모른다). 저장·공유된 다른 종류는 불러올 때 지운다
  - 참고 (⑦ 밖): 지금 확정 판정과 천장 전 확률도 그 배너에서는 같은 가정(학생마다 0.7%·50%)에 기대고, 천장 200에서 학생을 고를 수 있는지도 미확인이다 (`vanitas-dev-decisions.md` 8장). 그 배너의 한국 공지가 나오면 확인한다
- **구현 (⑦-2)**: `PlannerTarget.goal`(없으면 확정), `goalPulls(goal, 시작 스택, rule)`.
  결과마다 `goal`(고른 종류)·`pulls`(쓰는 연 수)·`guaranteed`(천장까지 닿음 — 계획에 들면 확보, 아니면 도전)·`probability`(그 연 수 안의 확률), `isPlanned(o)`(확보 또는 도전).
  대안의 목표 목록은 `securedIds` → **`plannedIds`**(확보 + 도전). 어댑터: `PlannerQuery.targets[].goal`, 고를 수 있는 목표의 `goalKinds`·`goalLock`(`multi_pickup`·`unknown_rate`)·`rateVerified`·`pickupCount`, `goalPullsRange()`(1 ~ 천장 − 1).
  고를 수 없는 종류·틀린 연 수가 와도 계산은 확정으로 하고 멈추지 않는다
- 시험 (⑦-2): 손으로 센 기준값(반천장 100연 = 12,000개, 다음 같은 종류 목표는 0에서, N ≥ 천장까지 → 확보, `half_passed`면 스택이 다음 목표로 이월, 뒤 순위 앞 날짜 목표 덕분에 도전), 확률이 `chargeProbAtLeastOne`과 같음, 여러 명 배너는 확정으로, 기존 무작위 60회에 종류를 섞어(계획만 다시 넣으면 모두 계획에 듦, 잔고가 0 밑으로 가지 않음),
  대안이 나오는 무작위 60회(잔고 고정 — 기존 무작위 검사는 잔고가 날마다 늘어 대안이 한 번도 나오지 않았다), 부족한 확률 목표의 메우는 방법(도전에서 멈춤).
  목표 종류를 고르지 않으면 예전 계산과 같은지 main의 `planner.ts`와 무작위 400회로 대조했다 (일회성, 레포에 두지 않음)

### 10-3. 화면 (⑦-3)

- **자리**: 내 목표 줄 안. 줄 아래에 한 줄을 더해 종류 고르기(확정 / 반천장까지 / N연까지), N연까지면 옆에 숫자 칸("연"). 목표마다 다르다
  - 지금 입력 부품(`SelectField`·`SegmentedField`, 48px)은 줄 안에 커서 작은 모양이 필요할 수 있다 — ⑦-3에서 375px·1280px 캡처로 정하고 디자인 문서 5-20에 남긴다
  - **구현 (⑦-3)**: 새 `GoalPicker.svelte` — `SegmentedField`와 같은 기울인 홈을 작게(조각 28px, 글자 12px, 모서리는 같은 단계 `3px 8px`·`2px 4px`), 라벨은 "확정 / 반천장 / N연"(낭독은 "{이름} 목표 종류").
    N연이면 옆에 연 수 칸(32px) + "연". 줄이 모바일(375px)에서 약 44px, 넓은 화면에서 약 49px 늘어난다. 모바일에서 N연 칸은 고르기 아래로 넘어가 약 82px
  - 여러 명 배너: 고르기 대신 "확정만 골라요 — 픽업 학생이 여럿인 배너는 반천장 규칙이 확인되지 않았어요" 한 줄
- **N**: 기본 50, 1 ~ (천장 − 1) = 지금 199 (천장은 `game-config`). 정수만. ~~범위 밖은 칸에 오류~~ →
  ⑦-3 구현: 입력 중에는 범위 안의 값만 바로 반영하고, 칸을 벗어날 때(또는 Enter) 빈칸은 이전 값, 범위 밖은 범위 끝(1·199)으로 고친다 — 다른 숫자 칸(`NumberField`)처럼 바로잡고 오류를 띄우지 않는다.
  다른 종류로 바꿨다가 N연으로 돌아오면 마지막 연 수를 다시 쓴다
- **줄 배지·문구**: "확보"(파랑)는 확정 목표에만

| 상태 | 배지 | 줄 문구 |
|---|---|---|
| 확정, 계획에 듦 | 확보 (파랑) | 천장 전에 나올 확률 N% (지금 그대로) |
| 확률, 계획에 듦 | **도전** (테두리) | 반천장까지 나올 확률 N% / N연 안에 나올 확률 N% |
| 계획에 못 듦 | 부족 (주황) | 청휘석 N개 부족 (+ 위의 확률) |
| 반천장을 지남 | 불가 (테두리, 지금 불가와 같다) | 반천장을 이미 지났어요. 확정이나 N연으로 바꿔 주세요 |
| N연이 천장까지 닿음 | 확보 (파랑) | N연이면 천장까지 닿아 확정과 같아요 |

- **추정 확률**: 1연 확률이 확인되지 않은 배너(`verified: false`, 지금 특별 픽업·페스)는 확률 옆에 "추정 확률" — 천장 계산기(`pity_badge_estimated`)와 같은 표시. 확정 목표의 천장 전 확률에도 같이 붙인다
- **결과판 색**: 파랑은 **모든 목표가 확보**일 때만 — 5-18의 "파랑 = 확보" 약속을 지킨다

| 목표들 | 판 색 | 판 배지 | 요약 (문구 초안, ⑦-3에서 다듬는다) |
|---|---|---|---|
| 모두 확보 | 파랑 | 확보 | 모두 확정으로 데려올 수 있어요 (지금 그대로) |
| 부족·불가가 하나라도 | 주황 | 부족 | 목표 4명 중 2명 확정 · 1명 도전 / N순위 ○○까지 청휘석 N개 부족해요 |
| 부족·불가 없이 도전이 섞임 | 색 없음 | 도전 | 모두 계획에 들어요 — 도전 목표는 그 연 수 안에 나오지 않을 수 있어요 |

- 결과 띠(모바일 고르기 탭): "목표 4명 · 2명 확보 · 1명 도전 · 7,918개 부족" (도전이 없으면 지금 문구). 도전이 있고 확보가 0명이면 "목표 2명 · 2명 도전"(⑦-3). 배지는 결과판과 같은 판정
- **구현 (⑦-3) 요약 문구**: 도전이 없으면 지금 문장 "목표 N명 중 M명 확정 가능", 있으면 "목표 4명 중 2명 확정 · 1명 도전"(확보 0명이면 "목표 2명 중 2명 도전").
  둘째 줄은 모두 확보 "모두 확정으로 데려올 수 있어요" / 도전이 섞임 "모두 계획에 들어요. 도전 목표는 정한 연 수 안에 나오지 않을 수도 있어요" / 부족 지금 문장
- 계획 판(기간별 계획)의 줄 색도 같은 규칙 — 그 기간 목표가 모두 확보면 파랑, 하나라도 못 들면 주황, 그 밖은 색 없음 + 도전. 연 수는 그 기간에 쓰는 연 수(확률 목표는 정한 만큼)
  - 구현 (⑦-3): 색 없는 줄은 흰색 60% + `navy` 15% 테두리 — 테두리 배지("도전", neutral)와 같은 "색 없음 = 테두리" 문법. 새 색 토큰은 없다
- 메우는 방법: 도전 목표가 계획에 드는 단계는 "도전" 배지 + "여기까지 바꾸면 계획에 들어요". 함께 계획에 드는 다른 목표도 "함께 확보:"·"함께 도전:"으로 나눈다 (⑦-3)
- 대안("더 많이 데려오는 방법"): 늘어나는 목표에 도전 목표가 있으면 "확보" 대신 "계획에 들어요"
- 계산 기준 접기에 한 줄: "확률 목표는 정한 연 수를 다 쓰고 마지막 연에 나온다고 보고 계획해요 (뒤 목표는 스택 0에서)" — 확률 목표를 하나라도 골랐을 때만 (⑦-3)
- 디자인 문서(`vanitas-design.md`, 프로젝트 문서): 5-18 판정 색 표에 "도전"(테두리, 색 없음) 행, 5-20에 줄 안 고르기 — ⑦-3에서 갱신안을 함께 낸다

### 10-4. 저장·공유

- planner 묶음에 **새 칸 `goals`**: 목표 키(`기간 id~학생 id`) → `"half"` 또는 `"<N>"`(문자열). 확정은 적지 않는다(기본 `{}`). 공유 링크 이름 **`gm`** (map-str):
  `gm=2026-11-17-fes-5-5th~rio.half,2026-12-08-dive-into-ocean~kokoro.50`
- **저장 판 번호(`vanitas:v1`의 `version`)는 올리지 않고, `targets`(`tg`)의 모양도 바꾸지 않는다** — 옛 저장값·옛 링크에는 `goals`가 없어 `sanitize`가 기본값 `{}`로 채우므로 모두 확정으로 읽힌다 (#55 스택 칸과 같은 방식). `tg`를 바꾸면 옛 탭이 새 형식을 못 읽고 빈 목록을 계정에 올릴 수 있다
- 칸 검사는 "문자열 값의 객체"까지만 한다 — `sanitize`는 칸이 검사에 걸리면 칸을 통째로 버리기 때문. 항목 거르기는 불러올 때(`persistSection`의 set):
  키를 `previousIds`로 잇고(`normalizeTargetKeys`와 같은 `resolveRecruitId`), 목표 목록에 없는 키·틀린 값(`"half"`도 1 ~ (천장 − 1) 정수도 아님)·여러 명 배너의 키만 뺀다. 목표를 빼면 그 키도 지운다
- 기간·학생 id에는 `.` `,` `~`가 들어갈 수 없다 — DB 제약(`20261111000000_game_data.sql`: 기간 `^\d{4}-\d{2}-\d{2}-[a-z0-9]+(-[a-z0-9]+)*$`, 학생 `^[a-z][a-z0-9_]*$`)과 관리자 화면 검사. map 형식의 `.`·`,`(`share.ts`)와 목표 키의 `~`가 겹치지 않는다
- 공개된 공유 링크 이름(`tg`·`rs`·`fr` …)은 바꾸지 않는다 (`vanitas-dev-decisions.md` 8장)
- 계정 맞추기 (⑥): 새 칸이 처음 쓰이면 지문이 바뀌어 계정에 한 번 올라간다 — 정상. 두 기기가 모두 새 판이면 내용이 같아 그대로. 묻기 창 요약(`summarize`)은 목표 수만 봐서 영향 없음
- **옛 탭 (받아들인다)**: 배포 전부터 열려 있던 탭은 `goals`를 모른다. 거기서 플래너를 고치면 `goals` 없이 저장되고(`sanitize`는 모르는 칸을 버리고 묶음을 통째로 쓴다) 계정에도 올라가, 다른 기기도 **목표 종류만 확정으로 돌아간다** (목표 목록은 그대로, 다시 고르면 된다).
  새 판 감지(SvelteKit `version.pollInterval` + `updated`)로 새로 고침을 권하는 것은 사이트 전체 일이라 발표 뒤에 본다
  → 2026-11-16 했다: 새 판 감지 + 탭 사이 저장(쓸 때마다 저장소를 다시 읽어 그 묶음만 바꾼다) — `docs/008` 3장

### 10-5. 하지 않는 것

- 목표 종류 통계 이벤트 — 발표 뒤 필요하면 (`analytics-events.md`, `src/lib/analytics.ts`)
