# 007. v0.3 — 로그인 저장과 목표 종류

> 작성: 2026-11-14 · 갱신: 2026-11-15 (⑥-2 로그인 화면) · 상태: ⑥-1 완료(#90), ⑥-2 시험 공개(`?accounts=preview`), 다음은 ⑥-3 맞추기
> 관련: `docs/006`(DB, 5장 보안, 8장의 "사용자 로그인 저장"), `docs/005`(플래너), `src/lib/state/`(브라우저 저장·공유·백업), `supabase/migrations/20261115000000_user_saves.sql`

## 1. 무엇을 하는가

v0.3.0은 두 갈래다. 기말 발표(11월 말) 전에는 ⑥을 끝내고, ⑦은 시간이 남으면 하고 아니면 발표 뒤에 한다 (2026-11-14 결정).

| 단계 | 내용 | 발표 전 |
|---|---|---|
| ⑥ 로그인 저장 | 구글·카카오로 로그인하면 입력값을 계정(DB)에도 저장한다. 브라우저 저장은 그대로 두고, 계정 값과 맞춘다 | **한다** |
| ⑦ 목표 종류 | 플래너 목표에 "반천장까지만"(스택 100), "확률로만"(정한 연 수만큼)을 더한다 | 시간이 남으면 |

바꾸지 않는 것: 로그인 없이도 지금처럼 쓴다(브라우저 저장). 공유 링크·백업 링크는 그대로다 — 계정과 관계없이 링크에 값이 담긴다.

## 2. 결정 (2026-11-14)

| 무엇 | 결정 | 이유 |
|---|---|---|
| 로그인 수단 | **구글 + 카카오** (이메일·비밀번호 가입은 막는다 — 관리자만) | 둘 다 Supabase가 기본 제공한다. 네이버는 기본 제공이 아니다 — "커스텀 OAuth 제공자"(2026-04, 무료 3개)로 붙여도 사용자 정보가 `response` 안에 한 겹 싸여 와서 중계 함수가 필요하고, 모두에게 열려면 네이버 검수 승인을 기다려야 한다 |
| 저장 단위 | 사용자마다 한 행에 저장 파일(`vanitas:v1`의 `{ version, sections }`)을 통째로 (`jsonb`) | 006 8장의 계획 그대로. 열로 나누지 않으므로 저장 형식이 바뀌어도 DB를 고치지 않는다. 읽을 때는 지금처럼 `parseSaveFile`·`persistSection`의 검사를 거친다 |
| 기기 값과 계정 값이 다를 때 | **한 번 묻는다** ("이 기기 값 / 계정 값"), 그 뒤로는 자동 저장 | 몰래 덮으면 한쪽 입력이 사라진다 |
| 확률 목표 | **연 수를 정한다** (예: 50연까지만) | ⑦에서 |

### 화면·카카오 (2026-11-14 결정)

- **H. 로그인 단추 자리**: 데스크톱은 왼쪽 목록 아래 "백업 링크" 바로 위(모든 화면), 모바일은 홈 화면의 같은 자리. 로그인하면 그 자리가 계정 단추(사람 + 확인 표시 선 아이콘, 2026-11-15 이름 첫 글자에서 바꿈 — 다른 아이콘과 같은 선 모양으로)로 바뀌고 누르면 계정 창(로그인한 제공자·저장 상태·로그아웃·계정 삭제)
- **I. 카카오 이메일**: 처음에는 "받지 않는다"로 정했으나 **바꿨다** — Supabase Auth의 카카오 제공자는 설정과 상관없이 `account_email`·`profile_image`·`profile_nickname`을 늘 요청한다(`supabase/auth` `internal/api/provider/kakao.go`, 2026-11-13). 카카오는 설정하지 않은 동의 항목을 요청받으면 KOE205로 막는다.
  → **개인 개발자 비즈 앱으로 바꾸고 이메일은 선택 동의**, 프로필 사진도 선택 동의로 켠다. 사용자가 이메일 제공을 거절해도 로그인되게 Supabase 카카오 설정의 "Allow users without an email"을 켠다. 우리는 이메일을 쓰지 않는다(저장값은 사용자 번호로 찾는다)
- **J. 로그아웃할 때 이 기기 값**: **그대로 둔다** (로그인 전처럼 이 기기에서 계속 쓴다). 계정 삭제 때도 계정의 값만 지우고 이 기기 값은 그대로 둔다

## 3. DB (`supabase/migrations/20261115000000_user_saves.sql`)

### 3-1. 표 `user_saves`

| 열 | 형 | 설명 |
|---|---|---|
| `user_id` | uuid PK → `auth.users` (삭제 시 같이 삭제) | 사용자 |
| `data` | jsonb | 저장 파일 `{ version, sections }`. 객체만, 64KB까지 (지금 저장값은 수 KB) |
| `updated_at` | timestamptz | 판. 저장할 때마다 바뀐다 — 다른 기기의 저장을 알아채는 데 쓴다 |

- **보안 규칙**: 로그인한 사람(`authenticated`)이 **자기 행만** 읽고·쓰고·지운다 (`user_id = auth.uid()`). 방문자(`anon`)는 아무것도 못 한다. 관리자도 남의 저장값을 보지 않는다
- 게임 데이터 표의 쓰기는 지금처럼 `is_admin()`이 막는다(006 5장) — 로그인을 열어 누구나 `authenticated`가 되어도 바뀌지 않는다. ⑥-2 전에 권한을 한 번 더 점검한다(6-3)

### 3-2. 함수

| 함수 | 하는 일 |
|---|---|
| `save_my_data(data, 먼저 읽은 판)` | 판이 같을 때만 저장하고 새 판을 돌려준다. 처음 저장이면 판 없이. 다르면 `P0001`(다른 기기에서 먼저 저장) — 화면이 묻는다. security invoker |
| `delete_my_account()` | 자기 계정을 지운다(저장값도 함께). 관리자 계정은 거부. security definer — `auth.users`를 지울 권한이 필요해서. 권한 확인은 `auth.uid()` 하나로 |
| `hook_before_user_created(event)` | Supabase Auth의 "Before User Created" 훅. **구글·카카오가 아닌 새 계정은 거부**한다 — 가입을 열어도 이메일·비밀번호 가입은 막힌다. Auth만 부른다(`supabase_auth_admin`) |

- 훅은 대시보드 Authentication → Hooks에서 고른다. 무료 플랜에서 되는지 적용할 때 확인한다 (안 되면 "Confirm email"을 켜 두고, 이메일 가입 계정은 권한이 없으니 그대로 둔다)
- 새 관리자를 대시보드에서 만들 때는 훅이 막는다 — 잠깐 끄고 만든 뒤 다시 켠다
- 로컬 시험(2026-11-14, Postgres 16 + 가짜 `auth`): 방문자 거부, 첫 저장·판으로 다시 저장, 옛 판·처음인 척 저장은 `P0001`, 객체 아님·64KB 넘음 거부, 남의 행 쓰기·읽기 불가, 손님의 게임 데이터 쓰기 거부(기존 규칙), 관리자 계정 삭제 거부·손님 계정 삭제 때 저장값 함께 삭제, 훅은 `email`·제공자 없음 거부, `google`·`kakao` 통과, 로그인한 사람은 훅을 부를 수 없음

## 4. 맞추기 규칙

이 기기에 `vanitas:sync` = `{ userId, syncedAt(마지막으로 맞춘 판), dirty(그 뒤 이 기기에서 고침) }`을 둔다. 저장값(`vanitas:v1`)과 따로 — 백업 링크·공유 링크에 실리지 않는다.

| 때 | 계정에 행 | 이 기기 | 하는 일 |
|---|---|---|---|
| 처음 로그인 (이 기기에 이 사용자의 sync 없음) | 없음 | — | 이 기기 값을 올린다 |
| | 있음 | 비었음(기본값) | 계정 값을 받는다 |
| | 있음 | 값 있음, 같음 | 그대로 |
| | 있음 | 값 있음, 다름 | **묻는다** (이 기기 값 / 계정 값) |
| 다시 열 때 | 판 = syncedAt | dirty | 올린다 |
| | 판 ≠ syncedAt | 안 고침 | 계정 값을 받는다 |
| | 판 ≠ syncedAt | dirty | **묻는다** |
| 고칠 때 | | | 브라우저에 저장(지금처럼) → 2초 모아서 `save_my_data`. 실패(오프라인)면 dirty로 두고 다음에 |

- "같음"은 저장 파일을 정규화(키 정렬)해 비교한다
- 계정 값을 받으면 화면이 다시 읽는다(백업 링크를 열 때와 같은 길 — `SavedStore.importFile`)
- 공유 링크로 연 화면(남의 값)은 저장하지 않는 지금 규칙을 따른다 — 계정에도 올리지 않는다

## 5. 화면

- **로그인 단추**(H): "로그인" → 고르기(구글 / 카카오) → 제공자 화면 → `/ko/auth/callback`으로 돌아와 원래 화면으로
- **계정 칸**: 로그인한 제공자, "계정에 저장됨 · 방금" 같은 상태, 로그아웃, 계정 삭제(한 번 더 묻고)
- **묻기 창**(4장): 두 값의 요약(목표 학생 수, 보유 청휘석, 마지막 저장 시각)을 나란히 보여 주고 고르게 한다
- **개인정보 처리방침** `/ko/privacy`: 7장. 정보와 출처 페이지·로그인 고르기 창에서 링크
- 문구 바꾸기: 정보와 출처의 저장 안내(`about_storage_body`), README "로그인 없이 자동 저장" — "로그인하지 않으면 이 기기에만, 로그인하면 계정에도 저장돼요"
- **번들**: supabase-js는 지금 `/admin`에만 있다. 방문자 화면은 로그인 단추를 누르거나 이 기기에 로그인 기록이 있을 때만 불러온다 — 로그인하지 않는 방문자의 첫 화면은 그대로 가볍게. Supabase 연결은 `/admin`과 한 곳(`$lib/supabase.ts`)으로 모은다

### 5-1. ⑥-2에서 만든 것 (2026-11-15)

- `$lib/supabase.ts`: 연결 하나. 관리자 화면은 바로(`supabaseWith`), 방문자 화면은 필요할 때(`loadSupabase`) — 로그인 기록(`sb-…-auth-token`)이 없으면 첫 화면에서 supabase-js를 불러오지 않는다 (시험으로 확인). PKCE 흐름
- `$lib/account.ts`(순수 함수·테스트)와 `$lib/account.svelte.ts`(상태): 시작, 로그인(돌아갈 화면을 탭에 기억), 돌아온 code를 세션으로, 로그아웃(관리자 표시도 지운다), 계정 삭제(`delete_my_account` 뒤 이 기기의 로그인 정보만 지운다)
- `AccountButton`: 왼쪽 목록(모든 화면)·모바일 홈의 "로그인 / 계정" 단추와 `<dialog>` 창. 제공자 단추는 글자만 (공식 단추 이미지는 받아 오면 바꾼다)
- `/ko/auth/callback`: code → 세션 → 시작한 화면으로(사이트 안의 경로만). 취소·가입 막힘·훅 거부·실패를 문장으로. 검색 제외(X-Robots-Tag)
- `/ko/privacy`: 개인정보 처리방침. 사이트맵에 더함
- **시험 공개**: `ACCOUNTS_OPEN = false` 동안 단추는 주소에 `?accounts=preview`를 붙인 브라우저에서만 보인다(`?accounts=off`로 끈다). 로그인한 기기에는 늘 보인다(로그아웃하게)
- 모바일 홈의 맨 아래 묶음(관리자·계정·백업)이 375×667에서 타일과 겹쳐, 모바일만 흐름에 두고 아래에 붙였다
- (2026-11-15 운영 시험 뒤) 구글로 로그인했는데 "로그인했어요"로 나왔다 — 관리자 계정(이메일)과 같은 Gmail이라 Supabase가 구글 로그인을 관리자 계정에 **이었고**, `app_metadata.provider`는 처음 만든 수단(`email`)이다. → 이 기기에서 고른 수단(`vanitas:auth-provider`, 관리자 화면의 비밀번호 로그인은 `email`)이 그 계정에 붙어 있으면 그것, 아니면 연결된 수단(identities) 중 마지막 로그인, 아니면 `app_metadata`. 이메일 로그인은 "이메일로 로그인했어요"
  - 이어진 계정이라 구글로 로그인해도 관리자다(같은 사용자). 계정 삭제는 관리자라 거부된다
- 계정 단추의 아이콘을 남색 원 + 흰 이름 첫 글자에서 **사람 + 확인 표시 선 아이콘**으로 (다른 단추처럼 선만, 2026-11-15)
- 시험 (로컬, 가짜 OAuth 게이트웨이 + Postgres): 플래그 없으면 단추 없음, 첫 화면에 supabase-js 없음, Google·카카오 로그인 → 시작한 화면으로, 새로 고침 뒤 유지, 플래그 off여도 로그인 중이면 보임, 로그아웃, 계정 삭제(저장값 함께)·관리자 계정 삭제 거부, 취소·가입 막힘·훅 거부 문장, 관리자 로그인 그대로

## 6. 설정 (사람이 콘솔에서)

### 6-1. 구글 (Google Cloud Console)

1. 프로젝트를 만들고 **OAuth 동의 화면**: 외부(External), 앱 이름 VANITAS, 지원 이메일, 범위는 기본(`openid` `email` `profile`) — 민감 범위가 아니라 심사 없이 게시할 수 있다. 앱 로고를 올리면 확인 절차가 붙으니 올리지 않는다
2. 홈페이지 `https://vanitas.live`, 개인정보 처리방침 `https://vanitas.live/ko/privacy`(⑥-2 배포 뒤), 승인된 도메인 `vanitas.live`
3. **사용자 인증 정보 → OAuth 클라이언트 ID**(웹 애플리케이션). 승인된 리디렉션 URI: `https://<프로젝트 ref>.supabase.co/auth/v1/callback`
4. 게시 상태를 "프로덕션"으로 (테스트 상태는 등록한 테스트 사용자만 로그인된다)

### 6-2. 카카오 (Kakao Developers)

1. 애플리케이션 추가 → **개인 개발자 비즈 앱 전환** (앱 → 일반의 비즈니스 정보, 결정 I)
2. 카카오 로그인 → 일반: 사용 설정 ON. OpenID Connect는 OFF 그대로 (Supabase 카카오 로그인은 쓰지 않는다)
3. 카카오 로그인 → 동의항목: 닉네임 필수, 프로필 사진 선택, 카카오계정(이메일) 선택 — 셋 다 켜야 한다 (Supabase가 셋 다 요청)
4. 앱 → 플랫폼 키 → **REST API 키**: 이 키가 Supabase의 Client ID. 같은 화면의 카카오 로그인 리다이렉트 URI `https://<프로젝트 ref>.supabase.co/auth/v1/callback`, 클라이언트 시크릿 발급·활성화 → Supabase의 Client Secret
5. "연결 해제 웹훅" 안내: 사용자가 카카오 쪽에서 앱 연결을 끊으면 알려 주는 기능. 받을 서버 주소가 따로 필요해 v0.3에서는 하지 않는다 — 사이트의 "계정 삭제"로 지운다 (나중에)

### 6-3. Supabase

1. Authentication → URL Configuration: Site URL `https://vanitas.live`, Redirect URLs `https://vanitas.live/**`, `http://localhost:5173/**`
2. Providers: Google, Kakao를 켜고 위의 값. 카카오는 "Allow users without an email" 켜기 (결정 I)
3. SQL Editor에서 `20261115000000_user_saves.sql` 실행 → Hooks에서 Before User Created에 `hook_before_user_created`
4. **가입 열기**: "Allow new users to sign up"을 켠다 (훅이 먼저 있어야 한다). 그 전에 Security Advisor 확인. ⑥-2를 운영 사이트에서 시험할 때 켜도 된다 — 로그인 단추는 `?accounts=preview`를 붙인 브라우저에만 보이고, 구글은 동의 화면이 "테스트" 상태라 테스트 사용자만 로그인된다
5. (선택) 배포 미리보기(`*.vanitas-xgi.pages.dev`)에서 시험하려면 Redirect URLs에 `https://*.vanitas-xgi.pages.dev/**`를 더한다. 없으면 로그인 뒤 운영 사이트(Site URL)로 돌아간다

2026-11-14 설정 완료: 훅, Google(동의 화면 테스트 상태·웹 클라이언트), Kakao(비즈 앱 전환·동의 항목·시크릿), Supabase Providers 둘 다 켬

## 7. 개인정보

법률 자문이 아니다. 개인정보보호위원회의 처리방침 작성 안내를 보고 맞춘다.

- 받는 것: 로그인 제공자가 넘기는 식별자, 이메일(구글. 카카오는 선택 동의한 경우), 이름·닉네임·프로필 사진 주소(제공자가 주는 대로 Supabase가 계정 정보에 둔다 — 계정 창에서 어느 계정인지 보여 주는 데만), 계산기 입력값
- 페이지: `/ko/privacy` (`src/routes/privacy`). 시행일은 로그인을 모두에게 여는 날(⑥-3)에 맞춘다
- 목적: 입력값을 여러 기기에서 이어 쓰기. 다른 데 쓰지 않고 넘기지 않는다
- 보관: 계정을 지우면 바로 지운다. 처리 위탁: Supabase(DB·로그인), Cloudflare(사이트 호스팅)
- 탈퇴: 계정 칸의 "계정 삭제"
- 익명 통계(Umami)는 지금처럼 쿠키 없이, 계정과 잇지 않는다

## 9. 위험

- 가입을 열면 누구나 `authenticated`가 된다 — 게임 데이터 쓰기는 `is_admin()` 함수·정책이 막고(006 5장), 훅이 이메일 가입을 막는다. ⑥-2 전에 `authenticated`에 준 권한 목록을 다시 본다
- 무료 플랜 한도: 월 활성 사용자·DB 크기는 이 사이트 규모에서 넉넉하다. 저장 크기는 행마다 64KB로 막는다
- 같은 계정을 두 기기에서 동시에 고치면 나중 저장이 묻기 창을 띄운다 (몰래 덮지 않는다)

## 10. ⑦ 목표 종류 (메모)

- **반천장까지만**: 그 목표에 스택 100까지만 쓴다. 반천장에서 ★3 확정·픽업 50%(`game-config` softPity)라 결과는 "확보"가 아니라 "그때까지 나올 확률". 확률 계산은 천장 계산기(`gacha.ts`의 반천장 분기)를 쓴다
- **확률로만**: 사용자가 정한 연 수(예: 50연)만 쓴다. 결과는 그 연 수 안에 나올 확률
- 정할 것: 두 목표가 계획에서 차지하는 청휘석(정한 만큼 다 쓴다고 본다), 못 뽑았을 때 남는 스택을 다음 기간으로 넘기는지(스택은 기간 간 이월 — 계획은 "다 쓰고 못 뽑음"을 최악으로 본다), 판정 문구(확보/부족 대신 확률), 공유 링크·저장 형식에 목표 종류 더하기(판 올림)
