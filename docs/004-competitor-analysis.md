# 004. 경쟁 서비스 분석과 포지셔닝

> 작성일: 2026-09-26
> 상태: **포지셔닝 확정** (① 결정 지원 + ② 재화 간 교환을 차별화의 두 축으로)
> 관련 문서: 기획서 1장(핵심 가치)·3-4(플래너)·8장(운영 주의), `sources.json`

---

## 1. 배경

이미 한국, 일본에서 VANITAS와 비슷한 포지션의 사이트가 운영중이다. 

이 문서는 세 서비스가 무엇을 하고 있는지, VANITAS와 어디가 겹치고 어디가 비어 있는지,
그래서 VANITAS의 방향을 어떻게 정했는지를 기록한다.

> 조사 범위: 2026-09-26, 로그인하지 않은 상태에서 볼 수 있는 화면 기준.
> 로그인 후 기능은 확인하지 못했다.

## 2. 서비스별 요약

### 2-1. 몰루로그 (mollulog.net) — 한국 서버

| 항목 | 내용 |
|---|---|
| 성격 | 미래시 + 커뮤니티 + 유틸 모음. 한국 서버 중심 |
| 미래시 | 일본 서버 기준으로 추정한 한국 일정. 이벤트·픽업·총력전·대결전·제약해제결전·캠페인까지 필터로 표시. 일정마다 유저 의견 |
| 청휘석 플래너 | 수급(이벤트, 총력전/대결전 등급, 임무, 전술대회 순위, 출석, 유료 패키지) + 소비(AP 충전) + 보유(청휘석, 10회·1회 티켓). 로그인 없이 사용 가능 |
| 타임라인 | 관심 학생을 고르면 픽업마다 **"남은 재화"**를 보여준다. 모집 목표 기본값은 "기댓값 (천장 반영)"으로, 한 목표당 12,960개(108연) 차감. 총력전 등 수급 일정이 사이사이에 들어간다 |
| 기타 도구 | 학생 성장, 재화/파밍, 이벤트 상점, 인연 랭크, 총력전 점수, 공략 타임라인 |
| 운영 | 로그인·프로필, 피드, 편성 통계. GitHub 공개 (코드는 Apache-2.0) |

**타임라인에서 관찰한 것** (사용자 직접 확인, 2026-09-26)
- 목표마다 남은 청휘석과 사용량을 **순서대로 차감해 보여줄 뿐**이다
- "확보 가능 / 부족 / 불가" 같은 **판정이 없다**
- 목표 사이의 **우선순위, 포기했을 때 무엇을 얻는지 같은 대안 제시가 없다**
- 차감 기준이 기댓값이라, "확정으로 데려올 수 있는가"(천장 기준)를 바로 알 수 없다

### 2-2. GachaPlan (gachaplan.com) — 일본 서버

| 항목 | 내용 |
|---|---|
| 성격 | 2026-07-29 일본 모집 개편(차지 방식) 전용 계산 도구 모음 |
| 호출 차지 계산 | 현재 차지·청휘석·티켓·모집 횟수 특전 → 남은 연차, 100·200 차지까지 부족분, 픽업 확률 |
| 그 외 | 2PU 우선순위와 둘 다 데려올 확률, 여러 미래 픽업의 장기 계획, 옛 포인트 방식 vs 차지 방식 비교, 모집 결과 기록 |
| 신뢰 장치 | 확률 공식·계산 전제·미지원 조건을 공개하는 방법론 페이지, 규칙 확인 현황과 갱신 이력. 확인 전에는 계산을 "잠정"으로 표시 |

### 2-3. Game8 (game8.jp) — 일본 서버, 대형 공략 사이트

| 항목 | 내용 |
|---|---|
| 선생님 레벨 계산기 | 현재 레벨·경험치·하루 청휘석 AP 구매 횟수 입력. 카페 600, 2주 패키지, 전술대회 상점 등은 **고정값**. 참고 표는 카페 AP와 레벨업 보너스를 반영하지 않음 |
| 청휘석 배포량 | 월별 무료 배포량 정리, 천장까지 걸리는 일수 |
| 데이터 이용 | 사이트 데이터·이미지의 무단 사용·전재를 금지한다고 명시 |

### 2-4. 그 외

- **天井計算スルヨちゃん**: 보유 청휘석 + 기간 + 월정액·반정액 + 주년 배포분 → 몇 천장 분이 모이는지. 입력이 단순한 수급 계산기
- 가챠 시뮬레이터 모음, 개인 블로그의 기대값 분석 글 다수

## 3. VANITAS와의 비교

| VANITAS 기능 | 몰루로그 (한국) | GachaPlan (일본) | Game8 (일본) |
|---|---|---|---|
| 픽업 플래너 | 타임라인으로 남은 재화 표시. **판정·우선순위·대안 없음** | 장기 계획, 2PU 우선순위 | — |
| 청휘석 수급 계산기 | 청휘석 플래너의 수급 계획 | 장기 계획 안의 수입 | 월별 배포량 글 |
| 천장·확률 계산기 | 플래너 안의 시뮬레이션 | **차지 방식 계산이 깊음** | 글 형태 |
| 레벨업 계산기 | 없음 | 없음 | 단순형 (고정값, 보너스 AP 미반영) |
| 재화 간 교환 (AP ↔ 청휘석 ↔ 레벨) | AP 충전을 소비처로만 받음 | 없음 | 레벨 계산기가 청휘석 계획과 분리 |
| 일본 서버 | 없음 | **주력** | 주력 |

## 4. 결정: 두 축으로 차별화한다

### ① 결정 지원 — "내 재화로 누구를 확정으로 데려올 수 있나"

몰루로그가 "남은 재화가 얼마인가"를 보여준다면, VANITAS는 **그래서 누구를 데려올 수 있는지**를 판정한다.

- 목표별 판정: 확보 가능 / 부족(N개) / 불가 (기획서 3-4)
- 안전 모드(천장 비용)와 기대값 모드를 전환해, "확정"과 "평균"을 구분해서 보여준다
- 우선순위에 따른 대안: "2순위를 포기하면 3·4순위를 천장까지 확보할 수 있다"
- 픽뚫 불가(특별 픽업)처럼 **놓치면 복각까지 기다려야 하는 목표**를 판정 문구로 구분한다
- 천장·확률 계산기의 판정 철학(천장 도달 여부로 결과를 나눈다)을 플래너까지 이어간다

### ② 재화 간 교환 — "AP를 사면 픽업을 몇 연 포기하나"

청휘석, AP, 레벨이 서로 얽혀 있다는 점을 하나의 상태 위에서 계산한다 (기획서 1장 핵심 가치).

- AP 구매 횟수가 레벨업 속도와 청휘석 잔고에 **동시에** 영향을 준다
- 레벨업 계산기와 수급 계산기가 같은 입력(하루 AP 구매 횟수, 보유 청휘석)을 공유한다 → `UserState`의 시작점
- 레벨업 계산기의 되먹임 계산(보너스 AP, 접속 횟수, 카페 랭크)은 확인한 범위에서 다른 도구에 없다

### 차별점으로 삼지 않는 것

- **미래시·일정 정보의 폭**: 몰루로그가 훨씬 넓고 커뮤니티로 유지된다. VANITAS는 판정에 필요한 만큼만 둔다
- **일본 서버**: GachaPlan이 차지 방식을 깊게 다룬다. 일본어판(3단계)은 차별점이 아니라 선택 과제로 본다
- **검증 상태 표시**: GachaPlan도 같은 방식을 쓴다. 차별점은 아니지만, 이 방향이 신뢰를 만드는 방식이라는 근거가 된다

## 5. 다른 서비스 데이터를 쓰는 원칙

일정과 보상 수치는 개발에 필요하므로 참고하되, 아래를 지킨다.

| 원칙 | 이유 |
|---|---|
| **공식 공지를 1순위로** 한다. 없을 때만 커뮤니티 사이트를 쓴다 | `sources.json`의 `tier`: `official` > `press` > `community` |
| 사실 정보(날짜, 보상 수치)만 옮긴다. 문장·표·이미지는 옮기지 않는다 | 저작물과 사실 정보를 구분 |
| 가능하면 **두 곳 이상을 교차 확인**하고, 출처 URL과 확인일을 `sources.json`에 남긴다 | 데이터 오류 재발 방지 (docs/002) |
| **자동 수집(스크래핑)과 API 호출은 하지 않는다.** 필요한 값은 사람이 확인해 입력한다 | 기획서 3-4 방침. 상대 서비스에 부담을 주지 않음 |
| Game8의 데이터는 **교차 확인용으로만** 쓴다 | 데이터 무단 사용·전재 금지 명시 |
| 몰루로그의 **소스 코드**를 참고할 때는 Apache-2.0 조건(저작권·라이선스 고지)을 따른다. 서비스의 데이터는 코드 라이선스와 별개로 본다 | 코드 라이선스는 "달리 표기하지 않는 한 소스 코드"에 적용 |
| GachaPlan은 이용 주의 페이지를 확인한 뒤 판단한다 | 미확인 |

## 6. 함께 발견한 것

- **한국 서버 차지 방식 전환 가능성**: 몰루로그 타임라인에 "모집 시스템 개편 기준 적용" 표시(11월 중순)가 있다.
  일본은 2026-07-29에 포인트 방식을 없애고 호출 차지와 모집 횟수 특전(70·130·150·170연에 10회 티켓)을 도입했다.
  한국이 전환되면 천장·확률 계산기와 플래너의 천장 비용이 바뀐다 → 공식 공지 확인 필요 (기획서 10장)
- **제약해제결전**: 총력전·대결전 외의 레이드. 청휘석 수급원이 될 수 있다 (로그에 초회 입장 보상 기록)
